# KWCAG 2.2 점검 노트 (persona-qa)

항목 조회용 문서입니다. 기본 QA 경로는 `references/persona-qa/kwcag-card.md`이며 이 문서는 필요한 번호만 조회합니다.

한국 제품의 접근성 결과를 KWCAG 2.2(한국형 웹 콘텐츠 접근성 지침 2.2)와 WCAG 2.2로 나란히 적기 위한 노트입니다. 인증 심사도, 법 준수 판정도, 법률 자문도 아닙니다. 흐름은 `references/persona-qa/workflow.md`(1-2단계는 5절, 5-6단계는 3-5절), 보고 틀은 `references/persona-qa/qa-report-template.md`(7절), 측정 검사는 `references/ergonomics/human-factors-checks.md`를 따르고, 이 문서는 한국 제품에서 달라지는 점만 더합니다. 문서끼리 다르면 더 엄격한 쪽을 따릅니다.

핵심 규칙:

- KWCAG 2.2와 WCAG 2.2는 따로 돌리고 따로 적음.
- 항목 번호·제목과 표준 구성은 국립전파연구원 공식 원문에서 읽은 사실로 적음(관찰됨 2026-09-30). WCAG 대응은 추론으로 따로 적음.
- 운영 환경의 본인인증, 인증번호, CAPTCHA에서는 멈추고 그 단계를 '미검사'로 적음.
- 법과 표준은 따로 인용하고 '준수'나 '위반'을 판정하지 않음.
- 결과는 본 화면에서 관찰한 커버리지이며 사용자 비율이 아님.

## 1. 표시와 확인 방법

KWCAG 표준 번호·개정일·구성·항목 번호와 제목은 2026-09-30 국립전파연구원 원문과 NIA 보도자료에서 읽었습니다. 나머지 사본·요약의 확인일은 2026-09-29를 유지하며 출처는 11절에 모았습니다. 항목별 WCAG 대응은 공식 매핑표가 없어 추론으로 둡니다. 제품별 동작은 미확인이므로 5절은 무엇을 기록하고 어떤 항목으로 볼지만 정합니다.

표시: 관찰됨(발행처·운영사의 원문·첨부·원본 저장소나 이 저장소를 직접 읽음), 미확인(미러)(제3자 사본으로만 읽음), 미확인(요약)(검색 요약으로만 봄), 미확인, 추론(이 문서가 사실에서 끌어낸 판단이며 표준이 낸 공식 대응이 아님), 규칙(이 스킬의 규칙), 미검사(멈췄거나 도구 밖이라 보지 못한 단계).

## 3. WCAG 2.2와 어떻게 다른가

### 3.1 큰 그림

- KWCAG 2.2는 WCAG 2.2의 한국판이 아님. 이름의 2.2는 KWCAG 자체 판 번호이고 바탕은 2018년 WCAG 2.1임([공식 원문][kwp], 관찰됨 2026-09-30). 그래서 한쪽 통과가 다른 쪽 통과를 뜻하지 않으므로 두 규칙 세트를 모두 돌려 따로 적음. 번호도 KWCAG는 5-8장(5.4.3), WCAG는 1-4장(1.4.3)이라 섞어 적지 않음.
- WCAG 2.2는 2023-10-05에 발행되어 2024-12-12에 오류 정정을 반영해 다시 발행됨. 새 기준은 2.4.11-2.4.13, 2.5.7, 2.5.8, 3.2.6, 3.3.7-3.3.9의 아홉 개이고 4.1.1 Parsing은 2023-01-25에 삭제됨. 근거: [w3c/wcag 변경 기록][wcagidx]. 관찰됨 2026-09-29.
- 표준이 낸 항목별 대응표는 찾지 못함. 아래 대응은 본문 대조(추론)임. 2022년 신규 9개 중 6.1.4, 6.5.1-6.5.4는 WCAG 2.1의 A 수준 기준에서 왔고, 7.2.2, 7.3.3, 7.3.4는 WCAG 2.2 신규 기준과 닮았으며, 6.4.4는 전자출판문서용이라 짝이 없음. 4절 표에 (신규)로 표시함. 신규 항목의 번호·제목은 [공식 원문][kwp]에서 읽음(관찰됨 2026-09-30). 대응은 추론으로 유지함.

### 3.2 WCAG 2.2에 있고 KWCAG 2.2 본문에서 짝을 찾지 못한 것

저장소 검사와 한국 흐름에 닿는 것만 뽑았으며 전수 대조가 아닙니다. KWCAG 본문에서 확대, 화면 방향, 상태 메시지, 입력 목적, 텍스트 간격을 요구하는 검사항목을 찾지 못했습니다. 보고서의 KWCAG 열에는 '없음(대응 항목 없음)'이라고 적습니다.

- 짝 없음: 1.3.4 Orientation, 1.3.5 Identify Input Purpose, 1.4.4 Resize Text와 1.4.12 Text Spacing(LY-01이 글자 잘림을 증상으로 봄), 1.4.10 Reflow(RF-01), 1.4.11 Non-text Contrast(PC-02), 3.3.4 Error Prevention (Legal, Financial, Data)(결제 흐름에서 관련됨), 4.1.3 Status Messages.
- 일부: 2.4.11 Focus Not Obscured (Minimum)(SM-06)은 6.1.2가 초점 표시만 다루고 가림은 다루지 않음. 2.5.7 Dragging Movements는 6.5.1 예시에 끌기와 놓기가 있음.
- 2.5.8 Target Size (Minimum)(PT-01): WCAG 2.5.8의 24 CSS px 최소 크기에 대응하는 항목은 없음; KWCAG 6.1.3은 대각선 6.0 mm와 1 px 안쪽 여백을 권장함(3.3절 (3)).
- 근거: [WCAG 성공 기준 원문][wcagsc] 관찰됨, [KWCAG 본문][kw] 미확인(미러), 대응은 추론 2026-09-29.

### 3.3 번호가 같아 보여도 판정이 갈리는 다섯 경우

근거: [KWCAG 본문][kw](미확인(미러)), [WCAG 성공 기준 원문][wcagsc]과 W3C 해설 [2.2.1][u221], [3.3.8][u338](관찰됨). 확인일 2026-09-29.

#### (1) 명도 대비: 5.4.3 대 1.4.3

- KWCAG 5.4.3은 본문 글자 4.5:1, 18 pt 이상 또는 굵은 14 pt 이상 글자 3:1에 더해 이렇게 적음: "화면 확대가 가능하도록 구현한 텍스트 콘텐츠(텍스트 및 텍스트 이미지)의 명도대비는 3 대 1까지 낮출 수 있다." WCAG [1.4.3][w143]에는 이 완화가 없고 3:1은 큰 글자에만 씀. 그래서 확대할 수 있는 화면의 3.5:1 본문 글자는 KWCAG 5.4.3의 완화에 들 수 있어도 WCAG 1.4.3에는 실패이며, KWCAG 통과가 WCAG 1.4.3 통과를 뜻하지 않음.
- PC-01은 WCAG 1.4.3만으로 판정하고 확대 완화를 적용하지 않음(규칙). KWCAG 열에는 '5.4.3: 확대 완화 해당 여부는 사람이 판단'이라고 적음. PC-01의 WCAG 판정과 KWCAG의 확대 완화를 각각 보고함.

#### (2) 깜빡임과 번쩍임: 6.3.1 대 2.3.1

KWCAG 6.3.1은 제목에서 "초당 3~50회 주기로 깜빡이거나 번쩍이는 콘텐츠를 제공하지 않아야 한다"고 적고 10인치 이상 화면 기기에서 특히 주의하라고 덧붙입니다. 세부 항목은 면적 조건과 정지 조건을 걸고, 셋째 항목은 번쩍이는 시간을 3초 미만으로 제한하는 방법을 서술합니다.

- 번쩍임, 면적 조건: "번쩍임이 초당 3~50회이며, 10인치 이상의 화면에 표시된 번쩍이는 콘텐츠가 차지하는 면적의 합이 화면 전체 면적의 10%를 넘지 않아야 한다."
- 깜빡임, 정지 조건: "초당 3~50회의 속도로 깜빡거리게 만든 콘텐츠는 그 깜빡임을 정지시킬 수 있어야 한다."
- WCAG [2.3.1][w231]은 1초에 3회를 넘게 번쩍이는 것이 없거나 번쩍임이 임계 아래일 것을 요구함. KWCAG의 3~50회에는 3회가 들어 있고, 면적은 화면의 10%로 적고 정지 조건을 따로 요구함(WCAG의 면적 기준은 임계 정의에 있음). GM-04는 WCAG 2.3.1과 ITU-R BT.1702를 따른 선별이며 인증이 아니고 초당 3회(전환 6회) 깜빡임을 통과시킴(표본 50 ms 허용). GM-04 결과가 통과든 실패든 6.3.1의 면적·화면 크기·정지 조건은 따로 확인함.

#### (3) 조작 크기: 6.1.3 대 2.5.8

- KWCAG 6.1.3: "콘텐츠에 포함된 모든 콘트롤은 대각선 방향의 길이를 6.0mm 이상으로 제공하는 것이 바람직하다." 안쪽 1픽셀 이상의 여백도 바람직하다고 적음. '바람직'은 권장이며 '해야 한다'가 아님. WCAG [2.5.8][w258]은 24×24 CSS px 이상이며 간격 등의 예외가 있음.
- 계산(추론): 대각선 6.0 mm인 정사각형은 한 변이 약 4.24 mm임. 24 CSS px는 휴대폰에서 약 3.8 mm(`references/ergonomics/human-factors-checks.md`의 파생값)라 대각선이 약 5.4 mm이므로, 2.5.8을 겨우 채운 타깃은 6.1.3 권장에 못 미칠 수 있음.
- PT-02는 터치 프로필에서 과업이 기대는 컨트롤이 기준에 못 미칠 때만 가로×세로 mm(`target_mm`)를 남김. 6.1.3의 대각선은 그 값으로 계산함(√(가로²+세로²)). 값이 없는 컨트롤과 안쪽 1 px 여백은 재지 않으므로 '미검사'임. 보고에는 WCAG 열에 2.5.8과 PT-01 결과를, KWCAG 열에 6.1.3과 대각선 mm 값을 따로 적음. 6.1.3은 '바람직' 수준이므로 결함 등급은 사용자 영향으로 정함(`references/persona-qa/evidence-and-severity.md`).

#### (4) 시간 제한: 6.2.1 대 2.2.1

- KWCAG 6.2.1은 시간제한을 해제하거나 연장하는 수단을 최소 20초 전에 알리라고 함. 보안 등으로 꼭 필요한 시간제한에도 벗어날 수단을 주라고 하고, 경매·실시간 게임 같은 예외에서도 시간제한이 있다는 것과 끝났다는 것은 알리라고 함. 세션 20시간 이상도 예외임.
- WCAG 2.2.1은 끄기, 조정, 연장 중 하나를 요구하고 실시간, 필수(essential), 20시간 예외를 둠. W3C 해설은 시간 기반 이중 인증 토큰처럼 보안 때문에 둔 제한을 필수로 볼 수 있어 면제될 수 있다고 적음([해설][u221]).
- 그래서 휴대폰 인증번호의 제한 시간은 두 열의 답이 달라질 수 있음. KWCAG 열에는 해제·연장 수단과 사전 안내의 유무를, WCAG 열에는 필수 예외의 가능성과 3.3.8을 적음. 남은 시간은 초 단위로 직접 기록함(CG-02는 토스트가 읽기 전에 사라지는지 보는 검사이며 카운트다운을 재지 않음).

#### (5) 인증: 7.3.3 대 3.3.8·3.3.9

- KWCAG 7.3.3: 인증이 인지 기능 테스트에 기대면 "인지 기능 테스트에 의존하지 않는 인증 방법을 적어도 하나 이상 제공해야 한다." 테스트의 예로 "로그인을 위한 비밀번호 입력", "특정 객체를 포함하고 있는 이미지 찾기" 등을 들고, 기대지 않는 수단의 예로 브라우저가 비밀번호를 저장할 수 있게 마크업한 서식, 신체(얼굴, 지문)나 물건(휴대폰, USB)을 쓰는 인증을 듦.
- WCAG [3.3.8][w338] (AA)은 물체 인식 CAPTCHA를 예외로 두고 3.3.9 (AAA)는 두지 않음. 그래서 물체를 고르는 CAPTCHA는 3.3.8에서는 예외에 들 수 있으나 KWCAG 7.3.3 본문을 그대로 읽으면 다른 인증 수단이 필요함(추론). 7.3.3은 3.3.8과 3.3.9의 사이에 있음.
- W3C 해설([3.3.8 해설][u338]): 붙여넣기와 자동 채움을 막아 옮겨 적기를 강제하면 다른 수단이 없는 한 실패임. 인증번호는 최소한 붙여넣기와 자동 채움이 되어야 하고, 소리를 옮겨 적는 방식은 대안으로 인정되지 않음. 코드 없이 앱에서 승인만 하는 방식은 인지 기능 테스트 없이 승인하는 예로 듦. CAPTCHA가 조건부로만 나타나도 적용되고, 3.3.8은 계정 생성이 아니라 기존 계정의 인증에 초점을 둠.
- 보고: KWCAG 열에는 7.3.3 관찰을, WCAG 열에는 3.3.8의 예외 해당 여부를 따로 적음. 한쪽 결과로 다른 쪽 칸을 채우지 않음.

## 4. persona-qa가 자주 만나는 검사항목

'저장소 검사'는 `references/ergonomics/human-factors-checks.md`의 검사 ID입니다. SM-08, FM-02, RF-01은 그 문서에 행이 없어 `ergoqa/checks.py` 등록부에서 읽었습니다. 검사 결과는 관찰 한 조각이며 항목 판정이 아니고, 통과가 항목 통과를 뜻하지 않습니다. ## 5. 한국 흐름에서 시험할 것

아래 흐름은 한국 서비스에서 접근성 문제가 나오기 쉬운 자리로 이 스킬이 고른 것입니다(규칙). 제품마다 구현이 달라 흐름마다 먼저 방식을 적고(관찰됨) 그 방식에 맞는 항목만 봅니다. 괄호 안은 KWCAG 2.2 항목 / WCAG 2.2 성공 기준이고 뒤의 ID는 저장소 검사입니다(4절). 제품별 동작은 모두 미확인이며 확인일은 2026-09-29입니다. 페르소나는 화면에서 본 사실만 적고 항목 판정은 하지 않습니다.

### 5.1 공통 규칙

- 실제 주민등록번호, 전화번호, 카드·계좌 번호, 공동인증서를 쓰지 않음. 팀이 준 테스트 신원과 테스트 번호만 씀.
- 운영 환경에서 본인인증, 인증번호, CAPTCHA를 만나면 에이전트는 멈추고 그 단계를 '미검사'로 적어 커버리지 진술에 남김. 읽기 계약의 중단 유형 `auth_gate`, `human_check`(`references/research/public-page-access.md` 5절)와 같은 뜻임. 이 문서는 인증이나 사람 확인을 건너뛰는 방법을 다루지 않음.
  - 멈추는 자리: 본인인증은 인증 화면이 열리는 데까지, 인증번호는 번호를 요청하기 전, CAPTCHA는 위젯이 나타나면, 결제는 결제창을 여는 버튼이나 결제 확정 앞, 공동인증서는 인증서 선택 화면 앞, 보안 키패드는 키패드가 뜨는 화면까지(실제 비밀번호는 넣지 않음). 주소 검색은 공개 화면이면 열어서 봄(테스트 주소만).
  - 제품 팀이 스테이징에 마련한 모의 인증, 테스트 번호, 테스트 결제 모드, 테스트 인증서가 있으면 그것으로 끝까지 검사함. 운영 환경의 통과 뒤 화면·실제 입력·결제 확정·서명은 '미검사'. 승인된 스테이징의 모의 절차는 테스트 데이터 권한 범위에서 완료·실패·복귀까지 검사함.
- 결제, 가입, 주문, 게시는 하지 않음(`references/persona-qa/workflow.md`의 읽기 전용 기본값). KWCAG의 적용범위는 제3자 서비스를 포함하므로 결제창·주소 검색·본인인증 화면의 결함도 제품 화면의 관찰로 적고, 수정 층만 제품 코드(연동 방식, 초점 처리, 대체 수단)와 제공사 위젯(제공사에 문의)으로 나눔.
- 관찰 범위: 웹 드라이버는 기본값으로 시나리오 출처 밖 요청을 막아 다른 출처의 결제창·주소 검색 위젯이 열리지 않을 수 있음. 출처를 더할지는 제품 팀이 정하며(`--allow-origin`, `drivers/web/README.md`), 열리지 않은 것은 결함이 아니라 '미검사'임. iframe 안은 드라이버가 다루지 않고(`references/ergonomics/platform-drivers.md`) 브라우저 밖 창과 앱 전환도 드라이버 밖이라 '미검사'임(추론). 드라이버 실행의 페르소나 에이전트는 기본값으로 스크린샷만 받고 접근성 트리는 `input_channel`이 `screenshot+a11y`나 `a11y`일 때만 받으며(`references/ergonomics/persona-agent-protocol.md`), 스웜은 스크린리더나 음성 제어를 구동하지 않음(`references/ergonomics/audience-research.md`). 이름, 레이블, 초점 같은 코드 수준 항목은 저장소 검사(SM-xx)나 그 채널에서만 볼 수 있음. 접근성 트리로 본 것과 실제 보조기술로 확인한 것을 나눠 적음.
- 페르소나에는 과업에 영향을 주는 접근 수단(키보드만, 화면 확대, 한 손 터치, 스크린리더)만 facet으로 붙임. 나이, 장애 유형, 말투로 능력을 추정하지 않음. 인앱 브라우저(웹뷰) 진입은 브리프에서 확인해 맥락 facet으로 적고, 재현하지 못하면 '미검사'로 적음.
- 팝업·레이어·앱 전환으로 열리는 화면(본인인증, 결제창, 주소 검색)의 공통 관찰: 누른 뒤에만 열리는가, 새 창이라고 미리 알리는가, 팝업 차단 때 안내가 있는가, 팝업창 제목이 있는가, 열리면 창 안으로 닫으면 누른 자리로 초점이 가는가, 닫기가 되는가, 돌아온 뒤 입력값과 진행 단계가 남는가. KWCAG 7.2.1은 새 창이 예측할 수 없게 열리지 않을 것과 닫으면 닫힐 것을 요구하고 레이어 팝업은 쓰지 않는 것이 바람직하다고 적으며, 6.4.2는 팝업창 제목을 요구함. (7.2.1, 6.4.2, 6.1.2, 7.3.4 / 3.2.1, 3.2.2, 2.4.2, 2.4.3, 3.3.7. FM-02는 레이어일 때만 읽힘)
- 인증 화면(본인인증, 인증번호, 보안 키패드, CAPTCHA, 공동인증서)의 공통 관찰: 인지 기능 시험(기억, 옮겨 적기, 퍼즐)에만 기대지 않는 수단이 하나 이상 있는가, 붙여넣기·자동 채움·비밀번호 관리자를 막지 않는가(3.3절 (5)). (7.3.3 / 3.3.8)

### 5.2 본인인증과 간편인증

- 먼저 적을 것(관찰됨): 열리는 방식(같은 창 이동, 새 창·팝업, 레이어, 앱 전환), 진입 경로(인앱 브라우저 여부), 제공 수단(통신사 본인확인의 문자·앱, 인증서·인증 앱으로 승인하는 간편인증 등), 제한 시간 유무, 스테이징 모의 인증 유무.
- 볼 것: 5.1절의 두 공통 관찰에 더해 인증 완료와 실패가 원래 화면에서 스크린리더에 전해지는가(짝 없음 / 4.1.3), 입력 칸의 레이블과 오류 안내(7.3.2, 7.3.1 / 3.3.2, 3.3.1. SM-03, SM-04)를 봄. 코드를 옮겨 적는 대신 앱에서 승인만 하는 방식은 W3C 해설이 인지 기능 테스트 없이 승인하는 예로 듦([3.3.8 해설][u338]). 제한 시간과 재요청은 5.4절.

### 5.3 보안 키패드

- 먼저 적을 것: 키패드 종류(키가 실제 버튼인지 그림인지), 배열이 바뀌는 때, 일반 키보드로 넣는 다른 경로 유무, 키패드가 뜨는 화면(로그인, 결제, 인증서 비밀번호).
- 볼 것:
  - 키 이름과 키보드: 키마다 접근 가능한 이름이 있고 스크린리더가 읽는가. 키보드로 고르고 누를 수 있는가. (5.1.1, 6.1.1, 8.2.1 / 1.1.1, 2.1.1, 4.1.2. SM-01, SM-08)
  - 다른 경로: 키패드 없이 넣는 경로가 있는가. 접근성 API로 쓸 수 없는 웹 애플리케이션이면 KWCAG 8.2.1이 대체수단을 요구함. (8.2.1 / 4.1.2)
  - 붙여넣기·자동 채움: KWCAG 7.3.3은 비밀번호 입력을 인지 기능 테스트의 예로 듦. 키패드가 붙여넣기와 자동 채움을 막으면 다른 인증 수단이 있는지 적음(3.3절 (5), 추론). (7.3.3 / 3.3.8)
  - 크기, 대비, 배열 변경: 키 크기·간격과 글자 대비(6.1.3, 5.4.3 / 2.5.8, 1.4.3, 1.4.11. PT-02, PT-01, PC-01, PC-02). 배열이 바뀔 때 알리는가. 알림이 없으면 위치로 키를 찾던 사용자가 다시 찾아야 함(추론). (짝 없음 / 4.1.3)

### 5.4 휴대폰 인증번호 시간 제한

- 먼저 적을 것(측정): 제한 시간(초), 남은 시간 표시 방식, 재전송·연장 수단, 입력 칸 구조(한 칸인지 자릿수별 칸인지).
- 볼 것:
  - 알림·연장·해제: 제한 시간이 있다고 미리 알리는가. 만료 20초 이상 전에 알리고 연장이나 해제 수단을 주는가. 재전송이 연장 구실을 하는가. 재전송해도 입력값이 남는가. (6.2.1, 7.3.4 / 2.2.1, 3.3.7)
  - 붙여넣기와 자동 채움: 자릿수별 칸이 전체 붙여넣기를 받는가. 브라우저나 문자 앱이 채울 수 있는가. 자릿수별 칸에 전체를 붙여넣어도 한 칸만 채워지는 것을 W3C 해설이 실패 예로 듦. (7.3.3 / 3.3.8)
  - 남은 시간 전달과 만료 뒤: 카운트다운을 스크린리더가 매초 읽어 방해하는지, 아예 알리지 않는지(추론). 만료 사실과 다음 행동을 알리는가. (짝 없음, 7.3.1 / 4.1.3, 3.3.1. SM-04)
- 저장소 검사는 전용 검사가 없음. 보고 열은 3.3절 (4), (5)를 따름.

### 5.5 CAPTCHA (보안문자)

- 먼저 적을 것: 종류(글자 옮겨 적기, 소리 옮겨 적기, 물체 고르기, 계산, 슬라이더·퍼즐), 나타나는 조건(항상인지 반복 실패 뒤인지), 대체 수단, 나타나는 화면(로그인, 가입, 게시).
- 볼 것:
  - 대체 형태: 목적을 알리는 텍스트와 다른 감각으로 하는 대체 형태가 있는가. WCAG 1.1.1에는 CAPTCHA 조항이 있으나 KWCAG 2.2 본문에서는 CAPTCHA를 다룬 조항을 찾지 못했음(5.1.1은 일반 규정). (짝 없음 / 1.1.1)
  - 다른 인증 수단: 소리 옮겨 적기와 조건부 CAPTCHA는 3.3절 (5)를 따름. 가입 화면의 CAPTCHA를 KWCAG 7.3.3의 '인증 과정'으로 볼지는 사례별 판단임(추론). (7.3.3 / 3.3.8)
  - 끌기·경로 동작, 키보드·스크린리더, 대비·크기: 슬라이더 퍼즐을 한 번 누르기로 대신할 수 있는가. 위젯에 닿고 조작할 수 있는가. (6.5.1, 6.1.1, 8.2.1, 5.4.3, 6.1.3 / 2.5.1, 2.5.7, 2.1.1, 4.1.2, 1.4.3, 1.4.11. PC-01, PC-02, PT-02)
- 에이전트는 CAPTCHA를 풀지 않음. 위젯의 종류, 대체 수단이 있다는 표시, 안내 문구처럼 화면에 보이는 것만 적음.

### 5.6 결제 모듈 팝업

- 먼저 적을 것: 결제대행사(PG)·간편결제가 결제창을 여는 방식(팝업, 레이어, 전체 화면 이동, 앱 전환), 제공사(화면에 보이는 이름), 세션 제한 시간, 테스트 결제 모드 유무, 데이터 변경 권한.
- 볼 것: 5.1절의 팝업 공통 관찰에 더해 다음을 봄.
  - 취소·실패 뒤: '결제되지 않음' 상태가 분명하고 주문 정보가 남는가. (7.3.4, 7.3.1 / 3.3.7, 3.3.1) KWCAG 7.3.1은 시스템·플랫폼 오류에 적용되지 않으므로 카드사·PG의 승인 거절은 대상이 아니고 입력 오류만 대상임.
  - 확인 단계와 제한 시간: 결제 전에 내용을 확인, 수정, 취소할 수 있는가(KWCAG에서 짝을 찾지 못함 / 3.3.4). 결제 세션 만료 안내와 연장이 있는가. (6.2.1 / 2.2.1)
  - 제3자 화면과 앱 전환: 창 안 컨트롤에 이름, 키보드 접근, 대비, 크기가 있는가. 접근성 API를 못 쓰는 모듈이면 대체 결제 수단이 있는가. (8.2.1, 6.1.1, 5.4.3, 6.1.3 / 4.1.2, 2.1.1, 1.4.3, 2.5.8) 앱으로 넘어갔다 돌아올 때의 화면과 주문 상태는 드라이버 밖이라 사람이 확인함.

### 5.7 주소 검색 팝업

- 무엇: 우편번호와 도로명주소를 검색해 주소 칸에 채우는 위젯. Daum 우편번호 서비스는 JavaScript API이며 팝업창으로 여는 `open`과 페이지 안에 끼워 넣는 `embed`(레이어) 두 방식이 있음([운영사 README][pcreadme]). 이 절의 사실은 이 서비스 기준이고 다른 위젯은 미확인임. Kakao 우편번호 서비스로 이름을 바꾸는 중이라는 검색 요약이 있으나 운영사 저장소는 아직 Daum 이름을 씀([hada.io][hada], 미확인(요약)).
- 먼저 적을 것: 여는 방식(팝업창/레이어), 주소 칸이 직접 입력 가능한지, 인앱 브라우저 진입 여부.
- 볼 것: 5.1절의 팝업 공통 관찰에 더해 다음을 봄.
  - 제목과 초점: `open`에는 제목을 정하는 `popupTitle` 옵션이 있고([패치 노트][pcpatch] 2021-08-03), 열릴 때 검색 칸으로 초점을 옮기는 `focusInput`은 기본 true임(2020-04-21). 값을 안 준 제목과 주소를 고른 뒤 초점 위치를 기록함.
  - 웹뷰와 팝업 차단: 운영사는 기본 웹뷰에서 `open`을 쓰면 팝업 대신 기존 페이지가 우편번호 페이지로 바뀌어 데이터가 전달되지 않으므로 `embed`를 권함(README FAQ 10). 팝업 방식이면 웹뷰에서 입력값이 사라지는지 봄. 팝업이 막히면 알리는 메시지가 뜨는데(패치 노트 2018-03-26) 보이고 읽히는가.
  - 검색 칸·결과·주소 칸: 레이블, 키보드로 결과 고르기, 결과 없음 안내. 채워진 값을 고칠 수 있는가. 읽기 전용 칸이면 값을 확인할 방법이 있는가. (7.3.2, 6.1.1, 7.3.1 / 3.3.2, 2.1.1, 3.3.1, 4.1.2)
  - 검색되지 않는 주소와 반복 입력: 도로명주소가 발급된 주소만 검색됨(README FAQ 1). 직접 입력이나 다른 수단이 있는가. 주문자와 수령자 주소가 같을 때 다시 검색하지 않고 고를 수 있는가. (7.3.4 / 3.3.7)
- 수정 층: 위젯 안 화면은 운영사가 색 테마와 버튼 숨김만 허용함(README FAQ 8). 위젯 내부 결함은 운영사 문의와 직접 입력 같은 대체 수단으로, 연동 방식은 제품 코드로 다룸. 확인: 운영사 저장소 관찰됨 2026-09-29.

### 5.8 공동인증서와 그 밖의 진입

- 공동인증서: 공인인증서는 2020-12-10 전자서명법 개정 시행 뒤 공동인증서로 불리며 화면에 옛 이름이 남아 있을 수 있음([korea.kr][esign], 미확인(요약)). 먼저 적을 것: 설치 필요 여부, 인증서 선택 창이 브라우저 안인지 밖인지, 비밀번호 입력 방식(5.3절), 다른 인증 수단 유무. 볼 것: 사전 설치가 필요하면 안내가 접근 가능한가, 접근할 수 없는 웹 애플리케이션이면 대체수단이 있는가(8.2.1, 6.1.1 / 4.1.2, 2.1.1). 브라우저 밖 창은 웹 검사가 읽지 못하므로 사람이 본 결과와 '미검사'를 나눠 적음.
- 앱과 키오스크: KWCAG의 대상은 웹 콘텐츠임. 앱의 법정 기준은 장애인차별금지법 시행령 제14조⑥의 검증기준(과기정통부 고시, 읽지 못함)이고, 키오스크는 디지털포용법 제20조와 시행령 제15조가 다룸(6절). 앱 화면에 KWCAG 항목을 인용하면 '참고'로만 적음. 저장소 다른 문서가 언급하는 KS X 3253(앱)과 KS X 9211(키오스크)은 확인하지 못함(미확인).

## 7. 보고에 적는 법

접근성 발견은 `references/persona-qa/qa-report-template.md` 발견 표의 두 열('KWCAG 2.2 item'과 'WCAG 2.2 SC', 한국어 보고서에서는 'KWCAG 2.2 항목'과 'WCAG 2.2 SC')에 따로 적습니다(규칙). 그 문서의 범위 칸에는 두 기준을 따로 적었다는 줄(Accessibility standards)이 있습니다. 한국어 보고서의 문체는 `references/research/korea/report-template.md`를 따릅니다.

- 두 열에는 `번호 제목`(예: 6.2.1 응답시간 조절), `없음(대응 항목 없음)`, `일부`와 이유, `미검사`, `미확인` 가운데 하나를 적음. 두 번호를 한 칸에 합치지 않음(5.4.3/1.4.3 금지). 저장소 검사 ID는 근거 열에 적음.
- 심각도는 P0-P3이며 사용자·제품 영향으로 정함(`references/persona-qa/evidence-and-severity.md`). 표준의 수준(필수, 바람직, A, AA)이 심각도를 정하지 않음.
- 결과는 커버리지임: '프로필 k개 중 n개, 이 화면, 이 조건'. 관찰됨, 추론, 미확인을 나눠 적음. "준수함"이나 "법을 위반함" 대신 "이 화면에서 KWCAG 2.2 6.1.1과 WCAG 2.2 SC 2.1.1에 해당하는 실패를 관찰함"처럼 적음.

커버리지 진술 문안(규칙):

> 접근성 점검은 KWCAG 2.2와 WCAG 2.2를 따로 했습니다. KWCAG 항목마다 사용한 판·출처와 공식 원문 또는 미러 대조 범위를 적었습니다. 대조하지 못한 문구는 미확인으로 남겼습니다. 스크린리더와 음성 제어는 사람이 확인하지 못했고 접근성 트리와 저장소 검사로 관찰한 것만 적었습니다. 운영 환경의 본인인증, 인증번호, CAPTCHA 단계는 미검사입니다. 이 결과는 커버리지이며 사용자 비율이나 법 준수 판정이 아닙니다.

## 8. 하지 않는 일

- 인증, 본인인증, 인증번호, 보안문자를 건너뛰는 방법을 쓰거나 적지 않음. 멈춘 자리는 '미검사'임.
- 실제 개인정보를 화면에 넣지 않음. 운영 환경에서 결제, 가입, 주문을 끝까지 하지 않음.
- 표준 통과나 법 준수를 판정하지 않음. '준수', '위반'이라 쓰지 않음. 법령을 해석하지 않음.
- 공식 원문과 대조하지 못한 항목 번호를 확정된 것처럼 쓰지 않음. KWCAG와 WCAG의 열을 합치거나 한쪽 결과로 다른 쪽 칸을 채우지 않음.
- 제3자 위젯의 원인을 제품 코드로 단정하지 않음. 나이나 장애 유형만으로 능력을 추정하지 않음. 실태조사 평균을 기준선으로 쓰지 않음.
- 다른 스킬 모음이나 도구 문서의 글·표를 옮기지 않음.

## 9. 완료 기준(Done when)

- 접근성 발견마다 KWCAG 2.2 항목과 WCAG 2.2 SC가 따로 적혔거나, 각각 '없음' 또는 '미검사'로 적힘.
- 만난 한국 흐름마다 열리는 방식, 본 항목, 멈춘 자리('미검사')가 적힘. 시간 제한은 초 단위 값으로 적힘.
- KWCAG 번호의 출처(공식 원문 또는 미러)가 밝혀지고, '준수', '위반' 표현이 없으며, 인용한 조항마다 판과 확인 표시가 있음.
- PC-01 판정이 WCAG 1.4.3 기준으로 적히고 KWCAG 5.4.3의 확대 완화는 따로 적힘.
- 못 다룬 것(스크린리더, 음성 제어, 실제 인앱 브라우저)이 커버리지 진술에 있고 실제 개인정보가 없음.

## 10. 실패 유형(Failure modes)

- 5.4.3을 1.4.3으로 적음(온라인판 오기를 따라감): 5장 번호를 씀. KWCAG 통과를 WCAG 통과로 읽음, 또는 반대: 두 열로 나눔. 확대 완화를 PC-01에 적용함: PC-01은 WCAG 1.4.3 그대로임.
- GM-04 결과를 6.3.1 판정으로 씀, 24 CSS px 통과를 6.1.3 충족으로 씀: 선별용 검사이고 휴대폰에서 24 CSS px는 6.0 mm 대각선에 못 미칠 수 있음.
- 인증번호 제한 시간을 WCAG 필수 예외로 끝냄, 물체 고르기 CAPTCHA나 붙여넣기를 막은 칸을 WCAG 예외나 보안 이유라며 넘김: 두 열을 따로 채우고 다른 인증 수단이 있는지 적음(KWCAG 7.3.3, 추론).
- 운영 환경에서 인증 단계를 넘기려 함: 멈추고 '미검사'로 적음. 열리지 않은 팝업을 결함으로 적음: 다른 출처 차단일 수 있으므로 제품 팀에 허용 출처를 묻고 '미검사'로 적음.
- 평균 70.4점을 기준선으로 씀, KWCAG 2.2를 최신으로 단정함, 지능정보화 기본법의 옛 접근성 조항을 지금 시행 중이라고 인용함: 각각 사이트 평균이고, 새 판 여부는 확인하지 못했고, 그 조항은 2026-01-22에 삭제되었음.
